# Integration health

Open **Home → View integration health** or **Settings → API health & frequency**. The checker starts with the real Waitress launcher and runs hourly by default while the server is running. Choose 15, 30, 60, 180, 360 or 1440 minutes, disable automatic checks, or request a check now. The development Flask launcher does not start the background checker. Scheduling settings take effect within about 30 seconds; computer sleep pauses checks, and missed intervals are not replayed as a burst.

Periodic checks use small, bounded requests to the existing Open-Meteo forecast and Google/BBC news feeds, configured Google Doc text exports and an official Google Calendar iCal URL. Private document/calendar data is read for a minimal format check, then discarded. No URL, credential, response body, document text, bank account or email content is written to health history. Redirects are limited to allowlisted official service hosts; calendar URLs hosted elsewhere are observed during normal use rather than probed by this checker. A successful health check proves availability and minimal response shape, not the correctness of every field used by the receipt.

Bank availability is observed through the existing finance checks, including partial/unavailable results. Gmail mailbox access, DVLA requests, Ticketmaster listing requests, Transport API, football API, ordinary Google Doc/calendar fetches and bin checks also report status when used. The background checker never refreshes bank tokens, re-downloads transactions, logs into Gmail, performs vehicle enquiries or spends paid API calls simply to test them. Unused observed integrations remain “Not checked”; missing Google document/calendar configuration is shown separately.

The page shows last check and success times in Europe/London, HTTP status when available, response time, consecutive unsuccessful checks and the latest 30 observations per integration. Older observations are labelled stale after at least two hours (or twice the configured interval if longer). Stale is not an outage; rarely used observed integrations can be stale simply because they have not been used. These samples are not an uptime percentage. Failure history uses fixed categories and never raw provider exceptions.

Checks avoid active print/preview workers, use a cross-process lock to prevent overlapping cycles, bound individual requests and response size, and limit manual cycles to at most one per 30 seconds. Status is stored privately in `data/api_health.json`, excluded from Git and backups; frequency preferences are included in the normal private settings backup. A failed health-history write does not break the underlying integration request. The server has to be running for automatic checks; no external alert or notification is sent.
